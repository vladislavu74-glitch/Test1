# Job Monitor — backend

Node.js + TypeScript сервис: ежедневно в 10:00 сканирует вакансии по
подтверждённым ресурсам найма, хранит состояние (скрыто/просмотрено, выбранные
названия должностей) и присылает письмо на email при появлении новых
вакансий. Обслуживает REST API для iOS-приложения из `../ios`.

## Быстрый старт (локально)

```bash
npm install
cp .env.example .env   # заполните значения, см. ниже
npx prisma migrate deploy
npm run seed            # заводит дефолтную запись критериев поиска
npm run dev              # запуск с автоперезагрузкой на http://localhost:4000
```

Проверка:
```bash
curl http://localhost:4000/api/health
curl -H "Authorization: Bearer <API_AUTH_TOKEN из .env>" http://localhost:4000/api/hiring-resources
```

Источники для скана вакансий не заводятся сидом — сначала запустите поиск
ресурсов найма (вкладка «Ресурсы найма» в приложении / `POST
/api/hiring-resources/discover`), см. раздел «Источники вакансий» ниже.

## Переменные окружения (`.env`, см. `.env.example`)

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | путь к SQLite-файлу |
| `API_AUTH_TOKEN` | токен, которым iOS-приложение авторизуется в API |
| `SUPERJOB_API_KEY` | ключ приложения SuperJob (зарегистрировать на api.superjob.ru) |
| `RESEND_API_KEY` | ключ Resend (resend.com/api-keys) для отправки email-дайджеста |
| `MAIL_FROM` / `MAIL_TO` | отправитель и получатель дайджеста (по умолчанию `vladislav.u74@gmail.com`) |
| `ANTHROPIC_API_KEY` | ключ Anthropic (console.anthropic.com/settings/keys) — нужен ИИ-агентам поиска источников вакансий и ресурсов найма (`src/discovery/*Agent.ts`) |
| `ANTHROPIC_PROXY_URL` | см. ниже — обязателен, если backend развёрнут на сервере с российским IP |
| `CRON_TZ` | таймзона ежедневного скана в 10:00 (по умолчанию `Europe/Moscow`) |
| `PORT` | порт HTTP-сервера |

### Anthropic API и российские IP

Anthropic API возвращает `403 Request not allowed` на ЛЮБОЙ запрос (не
только с `web_search`/`web_fetch`) с российских IP-адресов — это
гео-ограничение на стороне Anthropic, не проблема ключа или кода. Если
backend развёрнут на сервере с российским IP (как текущий продакшн),
задайте `ANTHROPIC_PROXY_URL="socks5://user:pass@host:port"` — адрес
SOCKS5-прокси на сервере в другой юрисдикции. `src/discovery/anthropicClient.ts`
заворачивает через него только вызовы Anthropic API, остального трафика
backend'а (hh.ru, SuperJob, Resend и т.п.) это не касается.

### Расход токенов Anthropic

`hiringResourceAgent.ts` и `aiSourceSearchAgent.ts` — агентные циклы: каждый
найденный ресурс (`report_resource`) или продолжающийся `pause_turn`
(длинная серия `web_search`/`web_fetch`) — отдельный вызов `messages.create`,
и без мер против этого каждый такой вызов заново оплачивал бы весь системный
промпт, описания инструментов и всю накопленную историю разговора. Против
этого:

- **Prompt caching** (`cache_control: {type: "ephemeral"}`) на system,
  на последнем инструменте в списке tools и на последнем подходящем блоке
  последнего сообщения — см. `withCacheBreakpoint` в обоих файлах. thinking/
  redacted_thinking блоки кэш не поддерживают, поэтому брейкпоинт ищется с
  конца до первого блока, который поддерживает.
- **`MAX_TOTAL_QUERIES`** (`hiringResourceAgent.ts`, сейчас 80) — суммарный
  предохранитель по числу `web_search`/`web_fetch` за весь прогон, отдельно
  от `max_uses` на один вызов API (актуально именно для report_resource-цикла,
  где вызовов API за один прогон может быть много).
- Кнопка «Остановить» в приложении (`POST /runs/:id/stop`) — ограничивает
  расход по времени/охвату вручную, не дожидаясь `finish_search` от модели.

Письма уходят через [Resend](https://resend.com) — HTTP API поверх порта
443, а не прямой SMTP: многие VPS блокируют исходящие SMTP-порты
(25/465/587) по умолчанию как антиспам-меру, порт 443 почти никогда не
блокируется (см. `src/mail/mailer.ts`). Без верификации своего домена в
Resend можно отправлять только с адреса `onboarding@resend.dev` (значение
`MAIL_FROM` по умолчанию) и **только на email, на который зарегистрирован
сам аккаунт Resend** — отсюда `MAIL_TO=vladislav.u74@gmail.com` по
умолчанию. Верификация домена (Dashboard → Domains, несколько DNS-записей)
снимает оба ограничения: можно будет слать с адреса на своём домене на
любой получатель.

## Источники вакансий

Источники для скана вакансий — это подтверждённые (`status: "confirmed"`)
записи `HiringResource` (см. ниже и раздел «Ресурсы найма» в приложении),
а не отдельная ручная таблица: ИИ-агент находит и верифицирует ресурсы
найма, и любой подтверждённый ресурс категории `direct_employer`,
`job_board`, `community`, `social` или `telegram` автоматически участвует
в следующем скане. Категории `recruiting_agency`/`hr_agency` в скан не
попадают — агентство подбирает под заказ для клиентов, у него нет
обобщённо парсибельного списка вакансий на своём сайте.

Коннектор для скана строится на лету из полей ресурса (`src/jobs/scan.ts`,
`toSourceRecord`):
- если у ресурса заполнен `scanConfig` (JSON вида `{"connector":"headhunter","areaId":113}`)
  — используется он как есть. Так заведены дефолтные источники со
  стабильным публичным API (`npm run seed`, см. `src/seed.ts`): hh.ru
  (Россия/Казахстан/Беларусь/Узбекистан/Киргизия), SuperJob, Habr Career —
  плюс доступны `ats_board` (Greenhouse/Lever, `{"provider":...,"boardSlug":...}`)
  и `rss_feed` (`{"feedUrl":...}`) для ручного добавления карьерных страниц
  на этих платформах;
- иначе (обычный ресурс, который нашёл ИИ-агент, без scanConfig) —
  `telegram` → `telegram_channel` (имя канала берётся из `t.me/<username>`),
  всё остальное → `generic_site` (обходит типовые пути карьерной страницы
  по адресу ресурса и вытаскивает JobPosting/эвристику по ссылкам, см.
  `src/connectors/genericSite.ts`).

Найденные ресурсы никогда не удаляются: повторный поиск добавляет новые,
обновляет данные у повторно найденных по тому же адресу и помечает
`isStale` те, что не подтвердились снова в рамках проверенных категорий —
таблица только пополняется/уточняется.

## Перенос каталога на другую установку (экспорт/импорт)

`GET /api/hiring-resources/export` отдаёт весь каталог ресурсов найма одним
JSON-файлом (формат `jobmonitor.hiring-resources`, с историей организаций
по имени, а не внутренним id — портируемо между разными БД). `POST
/api/hiring-resources/import` принимает такой файл (или голый массив
ресурсов) и upsert'ит их по нормализованному URL — как и обычный поиск,
не создавая дублей. Организации сопоставляются/заводятся по имени (см.
`resolveOrganizationId` в `src/discovery/dedupe.ts`). Импортированные
записи отмечаются `isNew: true` — для принимающей установки это
действительно новые данные. См. `src/discovery/hiringResourceTransfer.ts`.

## Как работает ежедневное уведомление

1. Каждый день в 10:00 (`src/scheduler.ts`) и по кнопке «Искать сейчас» в
   приложении (`POST /api/scan/run`) запускается `src/jobs/scan.ts`.
2. Для каждого выбранного пользователем названия должности (`JobTitle.selected`)
   и каждого подтверждённого сканируемого `HiringResource` вызывается коннектор.
3. Найденные вакансии сохраняются (upsert по `hiringResourceId+externalId`);
   по-настоящему новые (не встречавшиеся раньше) помечаются.
4. **Только для запуска по расписанию**: если есть новые и не скрытые
   вакансии — на `MAIL_TO` уходит одно письмо со списком (реальные ссылки,
   сортировка от свежих к старым), и они помечаются в `NotificationLog`,
   чтобы не продублировать письмо в будущем.
5. Кроме письма, новые вакансии видны и в приложении: `GET
   /api/vacancies` отмечает их `isNew: true`, `GET /api/vacancies/summary`
   отдаёт счётчик для бейджа на вкладке, а `POST /api/vacancies/:id/seen`
   (вызывается приложением при открытии конкретной вакансии) снимает
   пометку именно с неё.

## Тесты

```bash
npm test
```
Юнит-тесты коннекторов (generic-site, Telegram-канал) на моках HTTP,
интеграционные тесты пайплайна скана (новые/повторные вакансии, email
только по расписанию, скрытые вакансии не попадают в письмо, агентства не
сканируются) и API (авторизация, CRUD названий должностей, сортировка и
скрытие/показ вакансий, isNew/summary/seen) — на отдельной SQLite-базе.

## Деплой (чтобы скан в 10:00 реально срабатывал)

Ежедневный cron работает только пока процесс запущен — backend должен
быть развёрнут на постоянно работающем сервере (VPS, домашний сервер,
Docker-хост и т.п.), доступном с телефона:

```bash
docker compose up -d --build
```

`docker-compose.yml` поднимает контейнер с backend'ом, применяет миграции
при старте и сохраняет SQLite-базу в volume `job-monitor-data`. Не забудьте
`.env` рядом с `docker-compose.yml` и (один раз) `npm run seed` внутри
контейнера или через отдельный `docker compose run backend npm run seed`.
